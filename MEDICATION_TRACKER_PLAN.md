# Medication Tracking App - Development Plan

## Project Overview

A comprehensive medication tracking application that allows users to manage prescriptions, log medication intake, track side effects, and monitor symptom improvements. The system supports long-term prescriptions, short-term medications, and OTC drugs for ad-hoc use. Users can organize medications with custom tags for easy categorization and filtering.

## Tech Stack

- **Backend**: FastAPI (Python)
- **Database**: PostgreSQL
- **Frontend**: Modern web UI (React/Vue recommended)
- **Containerization**: Docker + Docker Compose
- **API Documentation**: OpenAPI/Swagger (auto-generated by FastAPI)

## Database Schema Design

### Tables

#### 1. `users`
- `id` (UUID, PK)
- `username` (VARCHAR, unique)
- `email` (VARCHAR, unique)
- `password_hash` (VARCHAR)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### 2. `medications`
- `id` (UUID, PK)
- `user_id` (UUID, FK → users)
- `drug_name` (VARCHAR)
- `pharmacy` (VARCHAR, nullable)
- `prescription_type` (ENUM: 'long_term', 'short_term', 'otc')
- `dosing_schedule` (JSONB) - flexible structure for various schedules
- `standard_dose` (VARCHAR) - e.g., "10mg", "2 tablets"
- `date_prescribed` (DATE, nullable)
- `date_filled` (DATE, nullable)
- `prescribing_doctor` (VARCHAR, nullable)
- `prescription_number` (VARCHAR, nullable)
- `notes` (TEXT, nullable)
- `active` (BOOLEAN, default true)
- `start_date` (DATE)
- `end_date` (DATE, nullable) - for short-term medications
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### 3. `medication_logs`
- `id` (UUID, PK)
- `medication_id` (UUID, FK → medications)
- `user_id` (UUID, FK → users)
- `taken_at` (TIMESTAMP)
- `dose_taken` (VARCHAR)
- `notes` (TEXT, nullable)
- `created_at` (TIMESTAMP)

#### 4. `side_effects`
- `id` (UUID, PK)
- `medication_id` (UUID, FK → medications)
- `user_id` (UUID, FK → users)
- `severity` (ENUM: 'mild', 'moderate', 'severe')
- `description` (TEXT)
- `occurred_at` (TIMESTAMP)
- `created_at` (TIMESTAMP)

#### 5. `symptom_tracking`
- `id` (UUID, PK)
- `medication_id` (UUID, FK → medications)
- `user_id` (UUID, FK → users)
- `symptom_name` (VARCHAR)
- `improvement_level` (INTEGER) - scale 1-10
- `notes` (TEXT, nullable)
- `recorded_at` (TIMESTAMP)
- `created_at` (TIMESTAMP)

#### 6. `tags`
- `id` (UUID, PK)
- `user_id` (UUID, FK → users)
- `name` (VARCHAR)
- `color` (VARCHAR, nullable) - hex color code for UI display
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)
- UNIQUE constraint on (user_id, name) - prevent duplicate tag names per user

#### 7. `medication_tags` (Junction Table)
- `medication_id` (UUID, FK → medications, ON DELETE CASCADE)
- `tag_id` (UUID, FK → tags, ON DELETE CASCADE)
- `created_at` (TIMESTAMP)
- PRIMARY KEY (medication_id, tag_id)

## Tag System Overview

The tag system provides flexible organization and categorization of medications. Users can create custom tags with colors and apply multiple tags to each medication for easy filtering and visual organization.

### Tag Use Cases

**Condition-Based Tags**:
- "Diabetes Management"
- "Blood Pressure"
- "Pain Relief"
- "Allergy"

**Time-Based Tags**:
- "Morning"
- "Evening"
- "Before Bed"
- "With Meals"

**Status Tags**:
- "As Needed"
- "Daily"
- "Active"
- "Ending Soon"

**Category Tags**:
- "Vitamins"
- "Prescription"
- "OTC"
- "Supplements"

### Tag Features

- **Color Coding**: Each tag can have a custom color (hex code) for visual distinction
- **Multi-Tag Support**: Medications can have multiple tags simultaneously
- **Filtering**: Filter medication list by one or multiple tags (AND/OR logic)
- **Tag Management**: Users can create, edit, rename, and delete tags
- **Auto-Suggest**: UI suggests previously used tags while typing
- **Tag Analytics**: View medications grouped by tags, see most-used tags

## API Endpoints (FastAPI)

### Authentication
- `POST /api/auth/register` - Register new user
- `POST /api/auth/login` - Login and get JWT token
- `POST /api/auth/logout` - Logout
- `GET /api/auth/me` - Get current user info

### Medications
- `GET /api/medications` - List all medications for user (with filters: active, type, tags)
- `POST /api/medications` - Create new medication entry
- `GET /api/medications/{id}` - Get specific medication details
- `PUT /api/medications/{id}` - Update medication
- `DELETE /api/medications/{id}` - Soft delete medication (set active=false)
- `GET /api/medications/{id}/schedule` - Get upcoming doses based on schedule
- `POST /api/medications/{id}/tags` - Add tags to medication
- `DELETE /api/medications/{id}/tags/{tag_id}` - Remove tag from medication

### Medication Logs
- `GET /api/logs` - Get medication logs (with filters: date range, medication_id)
- `POST /api/logs` - Log medication intake
- `GET /api/logs/{id}` - Get specific log entry
- `PUT /api/logs/{id}` - Update log entry
- `DELETE /api/logs/{id}` - Delete log entry
- `GET /api/logs/stats` - Get adherence statistics

### Side Effects
- `GET /api/side-effects` - List side effects (filterable by medication, date range)
- `POST /api/side-effects` - Report side effect
- `GET /api/side-effects/{id}` - Get specific side effect
- `PUT /api/side-effects/{id}` - Update side effect report
- `DELETE /api/side-effects/{id}` - Delete side effect report

### Symptom Tracking
- `GET /api/symptoms` - List symptom tracking entries
- `POST /api/symptoms` - Add symptom tracking entry
- `GET /api/symptoms/{id}` - Get specific symptom entry
- `PUT /api/symptoms/{id}` - Update symptom entry
- `DELETE /api/symptoms/{id}` - Delete symptom entry
- `GET /api/symptoms/trends` - Get symptom improvement trends

### Tags
- `GET /api/tags` - List all tags for user
- `POST /api/tags` - Create new tag
- `GET /api/tags/{id}` - Get specific tag details
- `PUT /api/tags/{id}` - Update tag (name, color)
- `DELETE /api/tags/{id}` - Delete tag (removes from all medications)
- `GET /api/tags/{id}/medications` - Get all medications with this tag

## Testing Strategy

### Testing Principles

1. **Test-Driven Development (TDD)**: Write tests before or alongside feature implementation
2. **Continuous Testing**: Run tests automatically on every commit via CI/CD
3. **Test Pyramid**: More unit tests, fewer integration tests, even fewer e2e tests
4. **Coverage Goals**: 90% backend, 80% frontend (with focus on critical paths)
5. **Fast Feedback**: Unit tests complete in seconds, full suite in minutes

### Testing Best Practices

**DO**:
- ✅ Write tests alongside feature development (TDD approach)
- ✅ Test one thing per test (single responsibility)
- ✅ Use descriptive test names (`test_user_cannot_access_other_user_medications`)
- ✅ Follow AAA pattern: Arrange, Act, Assert
- ✅ Use factories for test data generation
- ✅ Mock external dependencies (APIs, email, etc.)
- ✅ Test edge cases and error conditions
- ✅ Keep tests independent (no shared state)
- ✅ Use fixtures for common setup
- ✅ Run tests before committing code

**DON'T**:
- ❌ Test framework internals (trust FastAPI/React works)
- ❌ Write tests that depend on execution order
- ❌ Use real external services in tests
- ❌ Hardcode test data (use factories)
- ❌ Skip cleanup in tests
- ❌ Test implementation details (test behavior, not internal state)
- ❌ Ignore flaky tests (fix them immediately)
- ❌ Write overly complex tests (keep them simple)
